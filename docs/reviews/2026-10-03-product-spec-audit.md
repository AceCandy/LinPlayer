## 结论

**部分满足，尚不能认定全面符合。** Emby 主流程、共享播放解析、首页并发加载、缓存和按可见范围加载已有基础；但外挂字幕兼容、起播等待链、分页交付、失效请求取消和 API 能力降级仍有明确差距。现有检查也不能证明四端达到“快、丝滑”的目标。

本文是静态审查，不是实际测速。没有对 Yamby / Hills 做同条件比较，也没有以功能数量或技术栈推断体验优劣。P1 表示优先处理的功能或核心路径问题，P2 表示规模、资源或维护问题；优先级不代表已经测得故障发生率。

## 已确认的问题

### P1：Android Exo 路径未接入服务端外挂 WebVTT 字幕

- 服务端 `internal/service/emby_media_sources.go:400` 的 `mapSubtitleSelection` 给外挂字幕设置 `DeliveryUrl`，路径由 `embySubtitleDeliveryURL` 返回 `/Videos/{id}/Subtitles/{index}/Stream.vtt`。
- 服务端 `internal/handler/emby_playback.go:182` 的字幕 handler 以 `text/vtt` 返回内容。
- 客户端 `core/emby/playback.go:211` 优先使用 `DeliveryUrl`，地址选择本身与当前服务端匹配。
- 但 Android `ui/player/ExoEngine.kt:169` 的 `ExoPlayer.load` 只使用 `MediaItem.fromUri(url)`，没有附带外挂字幕配置；手机 `ui/player/PlayerPage.kt:353` 和 TV `tv/TvPlayerPage.kt:213` 的播放入口只把外挂字幕交给 `loadExternalAss`。
- `ui/player/PlayerPage.kt:1120` 的 `loadExternalAss` 只接收包含 ASS 脚本标记的内容，WebVTT 被跳过。

影响：在 Exo 内核下，服务端单独提供的外挂 WebVTT 不会被这条链路加载；内封字幕和 mpv 路径不能因此一并判定失败。

建议：保留 ASS 路径，将服务端返回的文本外挂字幕接入 Media3 字幕配置与选轨。验证手机和 TV 的默认字幕、手动切换、关闭字幕、切集及鉴权失败；不可仅验证地址能下载。

### P1：起播仍等待观看记录附加元数据，上报也延迟命令返回

`core/player/playback.go:118` 的共用 `play` 虽然并发获取 PlaybackInfo 与观看记录上下文，但在 `:152` 使用 `<-histCh` 等待后者，再执行实际播放。`buildHistoryContext`（`:410`）先请求条目，剧集再获取所属剧的 TMDB 标识。后续修复前复核发现 `SeriesProviders` 已有正、负缓存：只有未命中或前次请求失败时才请求剧标识，不能认定每集必定增加一次网络请求。缓存未命中时仍没有独立起播短预算。

这里需要区分两类数据：服务端进度、已看状态和片长影响续播正确性，不能简单跳过；剧标识等附加匹配数据是否必须等待，应根据跨服续播设置和已有数据决定。当前代码没有将它们分开。

此外，`:234` 在返回结果前同步等待 `ReportStart`。`core/emby/report.go:29` 使用 HTTP 请求；`core/httpx/httpx.go:151` 的响应头和读体空闲超时均为 30 秒，并非起播专用预算。上报失败不使播放失败，但等待仍存在。

影响：mpv 已经调用 `loadWith` 后才上报，不能说上报阻塞其首帧；Android Exo 要等返回结果才调用 `exo.load`，因此慢上报会直接延迟 Exo 起播。历史上下文等待发生在两种内核加载之前。实际延迟尚未测量，30 秒是网络空闲阈值，不是所有请求的固定总上限。

建议：优先消除 Exo 起播对上报完成的依赖，同时保证开始、进度、停止的顺序和会话一致性。将必要续播判据与可后补元数据分开，复用详情数据或受控缓存；不要以从头播放换取表面速度。

### P1：筛选能力没有按 MediaStationGo 的实际支持状态降级

`core/emby/filters.go:36` 的 `FiltersOf` 请求 Genres、Tags、Studios、OfficialRatings，另发年份探针。其 `record` 对 404 直接返回，不写入 `Unavailable`；`facet` 将成功空响应解析为空列表。

当前服务端 `internal/handler/emby_routes.go:179` 将 Genres 接到 `embyEmptyItemsHandler`；该 handler（`emby_static.go:106`）固定返回空 Items。当前两份 Emby 路由文件没有注册另外三个分面接口。

桌面 `Views/LibraryPage.cs:483` 依赖 `unavailable` 展示筛选失败或降级；因此这些“接口不存在 / 兼容占位”会被客户端当作正常空数据，无法准确表达能力缺失。服务端库里是否实际有类型数据，不应由该占位响应推断。

建议：建立基于当前服务端实现的明确降级行为，避免将占位接口视为可用分面。保留已支持的年份等能力，不擅自添加服务端端点，也不为补齐分面全库扫描。

### P2：收藏先拉全再显示，有静默截断上限

`core/emby/lists.go:355` 的 `Favorites` 调用 `fetchAllPaged(..., 2000)`；`:79` 逐页累积，全部完成后返回，达到上限不返回截断标记。桌面 `Views/MorePages.cs:460` 等整条命令返回才更新内容，换排序会重新发起加载。

影响：收藏较多时首屏需等待多页请求；超过上限时用户无法判断列表不完整。分集使用同一辅助函数，另有 10000 上限（`lists.go:344`）；不能将收藏上限误写成分集上限。

建议：收藏先交付第一页，再按需分页；排序必须核对服务端在对应库类型下的支持和结果，不能直接删掉原本为其他服务端保留的本地排序。需要本地排序时明确范围及截断状态。

### P2：桌面首页没有离页请求取消闭环

`Views/HomePage.cs:435` 的 `Track` 缓存命中后仍刷新，请求完成后写缓存、调用回调并排队更新控件；本文件未接入页面生命周期取消或失效代际检查。离页后已发请求仍可能继续占用网络与后续控件构建资源。

这是资源和生命周期缺口；本次没有复现跨账号界面被旧响应覆盖，不能将后者写成已发生故障。媒体库列表已有 `_gen` 检查（`LibraryPage.cs:657`），说明部分页面会拒绝旧响应，但拒绝结果也不等于取消网络请求。

建议：以页面生命周期和账号会话管理失效请求；同时保留正确的缓存隔离。验证快速切页、切账号和慢响应时的请求数量及资源释放。

## 仍不能认定达标的部分

1. **性能结果**：桌面已有 Perf 计时和 UI 调度延迟探针（`Core/Perf.cs`），旧审查也要求建立性能基线；本次未取得满足新规范的四端同条件数据。插件页面首帧检查不能代替视频首帧、首页可操作、seek 恢复或切集指标。
2. **真实 API 闭环**：本次未启动 MediaStationGo、未使用真实账号和片源联调。登录、分页、总数、Range、重定向、音轨、进度落地、已看及收藏需契约回归与实际操作验证，不能由路由存在或此前 CI 全绿代替。
3. **Android 起播收尾**：手机 `PlayerPage.kt:364`、TV `TvPlayerPage.kt:218` 直接等待 `loadExternalAss` 和 `loadEmbeddedFonts`；函数虽切到 IO，却是挂起调用，注释中的 fire-and-forget 不符合调用行为。它们在 `exo.load` 之后，不能据此断言阻塞视频首帧，但会延迟后续成功收尾，需核查慢字幕 / Range 对后台播放服务、弹幕等后续步骤的影响。
4. **规范维护**：`core/emby/emby.go:3` 仍将旧 Rust 行为写成逐字对齐的黄金实现，筛选和收藏注释也引用其他 fork 的历史结论。应保留故障经验，但不能继续作为当前服务端能力的最终依据。旧差分测试可保留，不应替代 MediaStationGo 契约测试。
5. **交互结果**：滚动、TV 焦点、拖动进度、切集动画与实际视频层未做真渲染或设备验证；本报告没有将异步结构直接等同于流畅体验。

## 建议处理顺序

1. 修复 Android Exo 外挂 WebVTT 接线，闭环实际字幕加载及选轨。
2. 收紧共用起播等待链：先处理同步上报，再区分必要续播数据与附加元数据，保证进度正确。
3. 对齐筛选及兼容占位的能力提示，补充针对当前服务端的契约样例。
4. 改善收藏首屏分页及截断提示，补齐页面请求取消和失效响应管理。
5. 对相关路径建立基线和联调记录；真机渲染可以另排，但功能修改仍需对应回归验证。
