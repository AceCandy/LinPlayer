# Android 启动闪退取证

用户反馈:红米 K80 Pro、Android 16,点击图标立即退出。尚未取得设备崩溃堆栈,根因未确认。

后续结果:V3 取得 WorkManager 初始化时缺失 Room 生成数据库无参构造器的堆栈,修复包已由用户在红米真机确认正常打开。修复与成品检查见 `2026-10-03-android-startup-fix.md`。以下保留诊断过程及其当时的验证边界。

## V3:复现完整启动

用户在 V2 上确认核心初始化成功,因此原生库加载、JNI/ABI 与核心初始化在该设备可用;不代表已经排除主进程 provider、Application、开屏或页面启动。历史系统记录仅显示 Java 崩溃,无堆栈。

V3 诊断页放在 `:diagnostics` 独立进程,Application 在该进程跳过核心初始化,不重复打开同一数据根。主进程保留原 provider 和 MainActivity 启动路径。按钮改为“测试播放器启动”,不再在诊断进程初始化核心。Application 的 `attachBaseContext` 提前安装 JVM 异常记录,覆盖 provider 初始化前的阶段;复制和恢复诊断页时重新读取主进程崩溃文件。

默认构建关闭诊断 Activity,保留主进程原行为。诊断构建跳过 Sentry 手动初始化与自动发送报告,报告只供用户主动复制。

验证:诊断完整单测 188 条通过。模拟主进程在页面打开后写入崩溃文件,复制时可读取并脱敏;新增提前异常记录回归通过,撤掉 attachBaseContext 记录后测试实际失败。独立源码复核未发现阻断问题,指出诊断主进程异常 handler 会被重复包装并写同一现场,不影响本次取证,暂未扩大修改范围。仍需真机取得完整启动结果。

V3 产物:`build/android-diagnostics/app-arm64-v8a-startup-diagnostics-v3.apk`。覆盖安装后应显示“启动诊断 V3”,点击“测试播放器启动”;若退出,回到诊断页点击复制。

## 已核实与改动

- 原手机 APK 的第三方原生依赖齐全,JNI 导出与 keep 规则对应,强引用符号可由 APK 库及最低 API 的 NDK stub 提供。ELF 段及 APK 压缩包的 16 KB 对齐检查通过。这些静态检查不等于设备上的加载成功。
- 新增编译期开关 `lp.startupDiagnostics`,默认关闭。正常构建保留 Application 中初始化核心层的行为。V2 诊断构建使用系统 `Application`,桌面图标直接打开系统控件诊断页,并禁用合并清单中的全部 provider。
- 用户主动测试核心加载后,捕获 JVM 异常并显示可复制的脱敏信息。原生崩溃不能被 JVM 捕获,再次打开可读系统退出描述和持久化启动阶段。V2 不启动播放器界面,不初始化 Sentry。
- 页面只读原有崩溃文件,不清数据;复制报告复用既有脱敏函数。诊断构建关闭 MainActivity 中的自动崩溃报告发送。
- 对旧桌面快捷方式直接启动 MainActivity 的情况,在开屏安装之前跳转诊断页。补充尚未创建 AppState 时的离页保护。上一版的 LinPlayerApp 初始化方法提取已撤回,正常 Application 无需修改。

## 使用与限制

V2 产物:`build/android-diagnostics/app-arm64-v8a-startup-diagnostics-v2.apk`。第一版保留用于对照,不再建议安装。

直接覆盖安装,不要先卸载。打开后应看到“启动诊断 V2”;先复制已有信息,再点“测试核心加载”。若再次退出,重新打开并复制诊断信息。诊断包不是闪退修复版,不能作为正常体验验收包。

未在红米真机安装,没有设备渲染与启动结果。若退出发生在诊断 Activity 打开前、系统不提供退出描述,或描述不足以定位原生崩溃,仍可能需要系统崩溃报告或 ADB 日志。Android 数据文件访问限制不影响本诊断页复制路径。
