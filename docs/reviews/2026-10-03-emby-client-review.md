# LinPlayer：Emby 客户端综合审查报告

审查日期：2026-10-03。代码基线：`78af5215aaa7b9e3f81014b090d8d55cbabf11c0`。

## 1. 结论与审查边界

LinPlayer 已经具备明确的差异化：跨服务器续播、多版本选择、弹幕、字幕、画质增强、多线程预取，以及桌面、手机、电视各自的界面。核心层共用、绑定生成、契约门禁、分页网格和历史故障记录也说明它具备持续演进的基础。

当前最需要补齐的是核心链路的完整性与失败后的恢复能力：用户能否找到全部内容，系统播放入口是否接通，下载完成的文件是否完整，更新失败后能否继续使用，故障是否被准确告知。继续增加扩展功能，对这些问题的帮助有限。

本报告按六个评审视角组织：Emby 集成、播放可靠性、安全与数据、桌面产品与设计、移动/电视产品与设计、架构与发布。它是一份基于代码证据的综合评审，不代表任何公司的实际背书或真实用户满意度调查。

### 证据等级

| 等级 | 含义 |
| --- | --- |
| A：静态确认 | 当前源码存在该行为或缺陷；不等于已在发行包/真机复现 |
| B：条件风险 | 实现存在风险路径，但是否触发取决于服务器、平台、调用入口或时序 |
| C：产品建议 | 定位、信息架构或体验取舍，不作为代码缺陷 |

优先级：P1 为优先处理的播放、内容完整性、数据、更新或凭据问题；P2 为后续可靠性、交互、性能及工程治理问题。此次没有足够证据将任何问题定为已经遭利用的 P0 漏洞。

### 实际做了什么

- 检查 Emby 登录、分页、搜索、播放解析、进度上报，以及核心播放器、历史、下载、预取、配置和更新实现。
- 检查桌面主要页面、Android 手机/TV 页面、Manifest、后台播放服务、绑定门禁及发布流程。
- 对各视角结果独立复核关键源码和调用链；移除或降级没有真实入口证据的结论。
- 阅读仓库已有桌面首页、播放器、登录页及手机首页截图，作为视觉现状参考；截图不代表当前代码的真实渲染验收。
- 运行两个现有 Python 静态门禁，并执行只读的 Manifest 类路径、服务调用及参数扫描核对。

未做：编译、核心层/平台单测、真实 Emby 联调、抓包、压力测试、Windows/Linux 真渲染、Android 真机、电视遥控器、屏幕阅读器或全量发行包重建。本次未启动服务、未修改业务代码。

## 3. 资深开发视角：Emby 业务与播放链路

### F01｜P1｜A：屏蔽过滤使全量分页提前结束

**证据：** `core/emby/lists.go:64-72` 的 `fetchItems` 返回前执行 `filterBlocked`；同文件 `:79-97` 的 `fetchAllPaged` 用过滤后的 `len(out)` 计算下一页偏移，并以过滤后 `got < 200` 判断结束。收藏和全剧分集分别调用它，见 `lists.go:340-345`、`core/emby/detail.go:345-350`。

**场景：** 服务端第一页原本有 200 条，其中 1 条被屏蔽，后面还有第二页。客户端看到 199 条后直接结束；第二页不是加载慢，而是根本不会请求。

**影响：** 用户只能看到一部分收藏或分集，很容易误以为服务器缺内容。横切屏蔽逻辑改变了分页层需要的原始条数。

**建议：** 分页使用服务端原始页长度/游标，过滤仅作用于展示结果；避免每个调用方各补一份翻页逻辑。

**验收：** 模拟两页、第一页 200 条且屏蔽 1 条；第二次请求偏移必须为 200，最终结果包含第二页、无重复，并覆盖整页全部被屏蔽的情况。

### F02｜P1｜A：本地筛选把“本页数量”当成“总数量”

**证据：** `core/emby/lists.go:249-262` 中，只要本地复筛删除任一条目，就将 `page.Total` 改成 `len(page.Items)`。源码明确记录了“只复筛当前页”的简化。手机/TV 媒体库根据总数控制停止加载，见 `ui/pages/LibraryPage.kt:197-211`、`tv/LibraryPages.kt:218-222`。

**场景：** 服务端不支持某个过滤条件，或评分上限只能在客户端执行；第一页筛后仅有 10 条，后面还有匹配内容。

**影响：** 当前结果看起来完整，实际仅覆盖第一页。该问题不只属于特殊 fork：代码未向服务端发送的筛选条件也可能触发本地筛选。

**建议：** 保留原始分页元信息，明确“筛后总数未知”；按原始游标继续抓取，直至满足展示页或原始数据结束。若暂保留上限，应准确提示结果不完整，不伪造一个确定总数。

**验收：** 首屏少量匹配、第二页更多匹配时仍可触达；无匹配的原始页不能被当成整个查询结束。

### F03｜P2｜A/B：搜索结果有硬上限，类型复筛不能补足匹配结果

**证据：** `core/emby/search.go:21-27` 先拉一页再类型过滤；`:87-94` 默认 50、最高 200，无分页游标。TV 的 `tv/SearchPage.kt:110-113` 传 60，没有继续加载路径。代码记录了某类服务器会忽略搜索时的类型条件。

**影响：** 同词命中较多、尤其包含分集时，用户看不到全部匹配内容；服务端忽略类型过滤时，前 60 条里只剩几条目标类型，也不会补取后续匹配项。

**建议：** 优先让核心搜索支持原始游标和“还有更多”，各端按需取页。暂不实现全量搜索时，应显示结果上限，引导缩小关键词；不能把截断结果描述成全部结果。

**验收：** 覆盖 61 条/201 条命中，以及首页结果大部分被类型复筛删除的服务器响应。

### F04｜P1｜A：TV 选集入口只取前 200 集

**证据：** `tv/DetailPages.kt:421-424`、`tv/EpisodePage.kt:107-110` 仅请求 `emby.seasonEpisodes(limit=200)`，选集栏消费同一列表。核心 `core/emby/detail.go:325-337` 明确只取一页且限制为 200，不会自动取全。

**影响：** 单季/父项超过 200 集时，第 201 集以后的内容不能从这些选集入口到达。不能因为常见电视剧短季而忽略长篇动画等边界。

**建议：** 复用现有分页接口按需续取；跳到当前集时允许定位对应页。不要改成每次拉全剧、拖慢常见短季。

**验收：** 201 集和更长父项中可选择最后一集，返回详情后焦点仍正确；第一页不等待所有集数下载。

### F05｜P1｜A：Android 后台播放服务声明、入口和契约没有接成闭环

**证据：** `apps/android/app/src/main/AndroidManifest.xml:114` 声明 `.player.PlaybackService`；实际类的包名位于 `ui/player/PlaybackService.kt:1`，是 `xyz.linplayer.app.ui.player`。全应用源码检索只发现该服务自身的 `start/stop` 定义，没有实际起播流程调用。Manifest 类路径只读核对也未找到被声明的类。

**影响：** 不能凭服务文件存在就认定前台服务、通知栏、MediaSession、音频焦点和后台保活已经可用。修正类路径后，还需要把生命周期接到真实播放入口。

**建议：** 先决定手机/TV、mpv/Exo 各自的后台播放承诺；在已有起播/停播生命周期接服务，修正 Manifest，避免开出第二套播放状态管理。

**验收：** 真机起播后服务、通知和媒体会话存在；进入后台、锁屏、返回前台、停止、切换内核均符合承诺；停播后服务及焦点正常释放。

**复核修正：** 服务内部还存在 `onSeekTo` 发送 `position_secs` 而核心只读 `pos` 的契约错误，见服务 `:62`、`core/player/transport.go:99-103`。瞬时焦点恢复只设音量、不续播，duck 后固定恢复 100，低版本没有旧 API 焦点释放。这些均应在接线时一并修正，但因当前入口未接通，本报告不把它们称为已经复现的锁屏 seek 或来电故障。

### F06｜P1｜A/B：无 Emby 会话的停播分支跳过完整清理

**证据：** `core/player/transport.go:56-62` 会话解析失败时仅执行 mpv `stop`。正常收尾 `core/player/playback.go:405-421` 还会清播放目标、关闭代理/缩略图、强制落历史、清历史上下文。

**场景：** 停播请求没有可解析的 Emby 会话，例如无活跃账号且未传原会话；具体 UI 路径是否能在播放中造成此状态需联调。

**影响：** “视频停了”不等于“资源和最后进度已经正确收尾”。本地清理不应依赖网络账号能否解析。

**建议：** 本地停播/落盘始终执行；只有上报部分依赖会话。复用已有 Stop 的清理步骤，避免旁路遗漏。

**验收：** 删除/切换账号、会话失效、无会话停止后，最后位置可恢复，代理已关闭，下一片不会读到旧上下文。

## 4. 资深开发视角：数据、并发和更新

### F07｜P1｜A：分段下载没有完整验证服务端 Range 响应

**证据：** `core/download/download.go:615-629` 发 Range 后仅拒绝 4xx/5xx，没有验证 206 和 Content-Range；`:631-667` 只检查“少于”段长度，不拒绝超长。`:842-867` 合并时没有最终长度检查，读取不到某 part 时直接继续。

**场景：** 探测阶段支持 Range，实际分段响应却变成 200 全文件或错误范围。当前短读防护不能拦住这个相反方向的错误。

**影响：** 超长内容被写入多个 part，再被拼接，任务仍可显示完成。缺 part 的合并路径也没有把缺失明确作为失败。

**建议：** 校验实际响应范围和精确段长；不支持 Range 时安全回退整流；合并前确认所有段，合并后校验总长度。先写最终临时文件，成功后再替换目标，不要先毁掉有效旧文件。

**验收：** 覆盖探测 206/实际 200、范围错位、超长、短读、part 缺失、磁盘写失败。任何一种都不得把损坏文件标为 completed。

### F08｜P1/P2｜A：下载及插件持久化的“原子写”不保证并发顺序

**证据：** 下载 `core/download/download.go:725-742` 在锁外把不同快照写入同一固定 `.tmp`，写/rename 错误被忽略；插件 `core/plugin/rt/storage.go:99-123,177-198` 也有锁外快照、固定 `.tmp`，KV flush 写前先清 dirty，写失败后无重试保障。

**影响：** 并发修改可能由旧快照最后覆盖新快照；磁盘错误可让内存状态与重启后的状态不同。临时文件加 rename 只能处理部分写入问题，不能自动解决顺序和持久化失败。

**建议：** 先复用一个串行落盘锁/通道，或唯一临时文件加状态代次；写失败保留待保存状态并提供可诊断错误。不需要引入数据库或通用存储框架。

**验收：** 延迟旧快照写入、并发修改新状态后重启；最终索引/密钥应为最新有效状态。注入一次写失败后确认重试与错误可见。

### F09｜P1｜A：更新复制失败仍删暂存、启动程序

**证据：** `core/system/update_install.go:319-327` 的 Windows 脚本在 robocopy 失败时只输出文字，随后照常删除 staged 并启动。Linux 分支也没有在 cp 失败后停止清理和重启。Windows 等待旧进程退出的错误被忽略。

**影响：** 文件占用、权限错误、磁盘空间不足或复制中断可能留下新旧混合版本，并删掉本可重试的更新负载。

**建议：** 第一阶段先做到失败立即停止、保留 staged、不给“安装成功”反馈；后续建立可恢复的旧版本备份/替换方案。不可把 userdata 纳入破坏性镜像覆盖。

**验收：** 在 Windows/Linux 分别注入复制失败、文件占用和写入中断；失败后旧版本可用、用户数据不变、负载可重试。已有成功路径测试不能代替这些失败检查。

### F10｜P1｜A：桌面更新资产只检查大小

**证据：** `core/system/update_install.go:164-168,190-205` 缓存及下载依据是 AssetSize，未核实内容哈希或发行签名；`.github/workflows/publish.yml:131-147` 已发布校验文件，但客户端没有消费它。

**影响：** 大小相同的错误文件或替换包可以通过已有检查。该结论不表示已经观察到攻击。

**建议：** 至少消费哈希以检测内容损坏；若要证明来源，需要用内置信任公钥验证签名元数据/资产。安装包与同源无签名哈希一起被替换时，哈希不能独立证明真实性。Android 系统 APK 签名校验与桌面路径应分开评价。

**验收：** 同大小、不同内容的负例必须拒绝；无效签名和错误版本/平台资产不得覆盖当前安装。

### F11｜P1/P2｜A/B：取消、重试、关停的并发状态没有统一提交规则

**证据：** 更新 `core/system/update_install.go:115-138,402-409` 取消后立即回 idle，旧 goroutine 结束时仍无条件写状态；bus `core/bus/bus.go:255-272,330-343` 的接纳检查与关停取消不是同一临界区。bus 8 worker、256 缓冲，Call 的 `jobs <- job` 可在满队列时阻塞，和“立即返回”契约不一致。

**影响：** 更新立即重试时旧任务可能覆盖新任务状态；关停竞态可接纳没有结果通道的命令；过载时宿主调用线程可能被阻塞。具体时序和用户影响需竞争/压力测试。

**建议：** 更新用任务身份限制旧任务提交；命令接纳与关停共享状态边界；定义队列满时的快速拒绝/排队规则。保留现有 worker 池，不能为“更简单”退回已记录风险的 FFI 内临时 goroutine。

**验收：** 覆盖“旧任务最后返回”“Call 与 Shutdown 并发”“worker 占满且队列满”；命令不永久悬挂，取消不覆盖后续任务，过载行为符合约定。

## 5. 安全、隐私和用户信任

### F12｜P1/P2｜A/B：下载索引保存包含账号 token 的完整地址

**证据：** `core/download/commands.go:75-83` 将 token 拼入下载地址，`Item.URL` 被 JSON 序列化；`core/download/download.go:725-742` 索引以 0644 创建。

**影响：** 地址本身包含凭据。Unix 上若上层目录可遍历，其他本机用户可读取；Windows 实际权限取决于 ACL，不能直接用 Unix 模式推断。该文件也可能被误分享或备份。

**建议：** 索引保存账号身份和无凭据资源引用，恢复时从会话重建认证；必要敏感文件使用私有权限。无需为了所有用户数据引入额外加密框架。

**验收：** 索引不含 bearer token；更换/撤销账号 token 后恢复下载逻辑明确；Linux 权限和 Windows ACL 分别检查。

### F13｜P1/B：手机遥控添加账号通过明文局域网链路

**证据：** `core/companion/companion.go:162-175` 建 HTTP 服务，`core/companion/page.html:392-395` 通过该页面 POST 账号密码。随机路径 token 用于认证，不加密传输。

**影响：** 在不可信网络、攻击者可观察链路的条件下，凭据可能被读取。并非所有同网段设备天然可抓到该流量，风险依赖网络位置和攻击条件。

**建议：** 首先明确“仅可信局域网”边界并提示；若目标要求抵御链路观察者，增加经过审查的加密配对传输。不要把换成另一个随机 token 误当作加密。

**验收：** 在可控测试网络抓包确认当前凭据可读，再验证目标方案；隔离 Wi-Fi 无法连通时给予准确说明。

### F14｜P2｜A：插件壁纸失败日志保留本地服务 token

**证据：** `apps/windows/LinPlayer.Desktop/Views/Wallpaper.cs:145-155` 把 token 放在资源路径，失败时记录完整 URL；`core/system/report.go:142-150` 会保留回环地址且未抹路径中的 token。

**影响：** 日志里存在当次进程有效的本地资源凭据，日志进入报告后也未被遮盖。其有效性限于本机服务及进程生命周期，不能夸大成远程长期账号泄漏。

**建议：** 记录资源相对路径及错误类别，不记录带凭据完整 URL；报告脱敏同时覆盖路径凭据。

**验收：** 缺失壁纸资源触发日志后，磁盘日志及最终报告均不包含测试 token。

### F15｜P2｜B：不同上报通道的脱敏口径不一致

**证据：** 核心反馈 `core/system/report.go:125-150` 遮盖服务器主机；桌面 Sentry `Telemetry.cs:40-57` 仅处理主目录和凭据参数；Android `Telemetry.kt:30-45` 也是参数脱敏。是否有实际异常携带服务器地址进入 Sentry，本次未观测出站事件。

**建议：** 对隐私承诺建立共用的测试语料，各语言实现相同出站判据；测试最终 SDK 信封，不能只测试某个 Scrub 函数。避免只修一个日志入口。

**验收：** 注入假服务器地址、查询凭据、路径凭据、本地路径及异常嵌套值；在所有出站通道确认不残留应遮盖内容。

### F16｜P2｜B：迁移配置文件时权限可能变宽

**证据：** `core/config/adopt.go:47-50,95-112` 复制含账号凭据的 config 文件时使用 os.Create；常规配置保存 `core/config/config.go:144-161` 使用私有临时文件。

**建议：** 迁移时保留或显式设置私有权限。以受控 umask 检查 Unix 目标权限，Windows 单独检查 ACL；不要声称所有平台都已泄漏。

**产品信任建议：** 自动崩溃上报是现有明确选择，README 也已说明，不认定为“未经披露收集”。可以在设置中清楚呈现发送什么、何时发送、如何关闭；导出含凭据配置继续保留现有警示，不能宣传为强加密保险箱。

## 6. 产品经理视角：定位、任务完成率与需求顺序

### 6.1 需要承认的定位边界

`core/emby/playback.go:142-164` 明确只走原流，不使用 TranscodingUrl；设备档案 `:46-56` 也没有转码 profile。这是记录过的产品决策，不是漏写转码分支。本报告不建议违背该决策自动加转码。

因此，产品更适合“重视原画、本地设备有解码能力、网络有余量的 Emby 用户”。如果对外承诺普通手机移动网络、低性能电视也广泛可用，就必须准确说明原流的硬件/带宽边界，并提供可诊断错误及合适版本选择。

插件的完全信任也是既定设计，不能仅因插件可调用宿主能力就称存在沙箱漏洞。需要的是安装前信任说明、来源展示、禁用/回退和安全模式验收，而不是无需求重建整个权限系统。

### 6.2 用户任务比功能数量更重要

| 用户类型 | 核心任务 | 当前应优先补齐 | 暂不应扩大 |
| --- | --- | --- | --- |
| 桌面日常用户 | 打开后继续昨天那一集 | 准确续播、故障重试、完整分集、稳定更新 | 更多首页轨道和后台服务种类 |
| 手机用户 | 出门/锁屏后仍可控，换网络不丢进度 | 后台链路、系统控制、网络恢复、可用版本提示 | 更复杂的画质配置入口 |
| TV 家庭用户 | 少输入、遥控器能一路操作 | 扫码安全边界、焦点、长剧选集、返回路径 | 更多需要文字输入的高级设置 |
| 多服务器用户 | 找到同一片的版本并正确续播 | 账号身份、来源解释、跨服匹配可信度 | 默认自动替用户换到难以解释的版本 |

### 6.3 产品层应补的最小信息

- 搜索/筛选触达上限时，说明结果被截断，而不是让用户认为库里没有。
- 原流不可播放时，区分服务器拒绝、网络不足、解码失败和渲染失败；给出与原因对应的下一步，不只建议重试。
- 续播位置来自本地、当前服务器还是另一台服务器，应能在需要时查清；不能让技术细节挤占默认播放路径。
- 缓存数据继续展示时，轻量说明尚未刷新；失败时不清空用户仍可用的旧内容。
- 设置按观看任务组织，例如字幕/音轨、网络/线路、设备能力、扩展组件；已有高级项可以保留，但普通用户不必理解 mpv 参数才开始观看。

这些是体验建议，不是本次已证明所有对应文案都缺失。实施前应按具体页面核对已有表达，复用现成组件。

### 6.4 建议的衡量方式

先在固定测试设备、片源与网络环境取得基线，再制定指标；本次没有测得启动、首帧、卡顿或续播成功率，不能给出虚构评分。

建议观察：登录到首播完成率、冷/热起播 P50/P95、seek 恢复时间、播放失败原因、停播后续播位置偏差、完整分页是否遗漏、更新失败后恢复率。稳定性指标可在自动验收和用户主动诊断包里取得，不要求默认采集观看行为。

## 7. 设计师视角：信息层级、操作可达性和状态表达

### F17｜P2｜A：继续观看的双路失败被显示成正常空结果

**证据：** `apps/windows/LinPlayer.Desktop/Views/HomePage.cs:394-415` 对 Resume/NextUp 分别吞异常为空列表，`:442-502` 以正常空态展示或写入缓存。单路失败时保留另一条结果，是合理降级。

**建议：** 不做全仓库“大重构”。以 F05/F06/F11 的真实状态交接问题为边界，统一必要的起播/停播/系统控制，再在修改时提取已有重复逻辑。保留现有核心层、原生壳、组件系统和测试基础。

可观测性也应服务于故障定位：记录起播阶段、版本选择、网络/解码/渲染失败类别、任务代次和更新应用结果。现有 FFI 分配/释放计数、队列停滞指标、性能日志应优先复用，不必新增监控平台。

## 9. 已做对的部分：改进时应保留

| 能力 | 已有实现 | 为什么值得保留 |
| --- | --- | --- |
| 核心与壳分层 | Go 核心 + C ABI/事件，原生壳 | 各端共用协议与历史判据，少一类跨端分歧 |
| FFI 安全边界 | ABI 协商、字符串立即复制、panic guard、alloc/free 计数 | 可诊断错配和泄漏，避免进程突然退出 |
| 事件背压 | 结果不随意丢、高频状态合并、日志丢弃计数、EOF | 已有明确策略，应在其上解决接纳/关停竞态 |
| 绑定与契约 | 生成 C#/Kotlin 绑定、注册表双向检查 | 避免命令名漂移，但还需覆盖系统入口参数 |
| 首屏加载 | 首页分块、缓存优先、骨架；详情头部不等全分集 | 真正改善等待感，不能为了统一加载改回全量屏障 |
| 长列表 | MediaGrid、播放分集抽屉已有虚拟化 | 扩展到实际受规模影响的列表即可 |
| 多版本/续播 | MediaSource 选择、跨服匹配、本地历史、正常停播强制落盘 | 已有差异化，不宜换成 UI 自行拼地址/猜进度 |
| 网络边界 | 空闲超时公共层、预取取消/seek 测试、TLS 显式例外 | 修复时查既有经验，不应靠全局放松 TLS 或加大超时掩盖 |
| 本地服务/插件安装 | loopback、token、来源白名单；ZIP 路径/大小保护 | 已有实际安全措施，不能报告成完全无防护 |
| 配置与导出 | 普通配置临时文件+Sync+rename，含凭据导出有警示 | 将正确做法复用到下载/迁移/插件持久化 |

上一轮开源核查另已确认可选补帧运行包带专有许可组件，并存在 DirectML 的 MIT 标注问题。这属于发行与信任治理事项；不把“使用非开源可选依赖”当作 Emby 播放功能缺陷，但应准确呈现许可和安装边界。

## 10. 建议路线：按验收关口推进，不给未经估算的工期

| 阶段 | 工作 | 完成判据 |
| --- | --- | --- |
| 第一关：核心正确性 | F01/F02/F04 分页，F05 后台接线，F06 停播，F07 下载，F09 更新失败 | 每项有忠实负例；正常路径与边界均通过；不再静默遗漏/损坏/错误重启 |
| 第二关：数据与信任 | F08 持久化、F10 更新验证、F11 任务提交、F12–F16 凭据/脱敏 | 并发及失败注入可恢复；输出不含应遮盖测试凭据；旧版和用户数据可保全 |
| 第三关：操作完成率 | F03 搜索、F17 空/错状态、F18 键盘、T01–T07 真设备 | 各端只用目标输入方式完成核心路径；状态有准确下一步 |
| 第四关：规模与治理 | F19 列表成本、F21–F24 门禁/发布/文档/维护 | 有固定基线、平台发布门禁与状态证据；相同问题不再在另一个入口重现 |

不建议先做：换技术栈、全量拆文件、建设通用存储层、引入新的 UI 框架、一次性重写所有契约、默认上报观看行为或扩充更多内容源。它们不是此次核心问题的必要解法。

## 11. 最小发布验收矩阵

| 维度 | 必须覆盖的组合 | 成功判据 |
| --- | --- | --- |
| 登录 | 正确、错密码、过期 token、200 缺字段、多线路 | 只有有效会话持久化，失败原因准确 |
| 内容完整性 | 199/200/201 条；屏蔽首项/整页；客户端复筛 | 不重复、不漏后页、不把未知总数伪装为本页数量 |
| 搜索 | 多于 60/200 命中；混合类型；聚合部分失败 | 上限透明或可继续，成功服务器结果不被失败拖没 |
| 选集 | 长季、当前集不在首屏、换季返回 | 最后一集可达，焦点及滚动定位正确 |
| 播放 | 冷/热起播、切版本、seek、暂停、退出、重启续播 | 会话正确，最后位置正确，旧上下文不串入下一片 |
| 设备能力 | 常见 AVC/HEVC、不同音轨、ASS/PGS；mpv/Exo | 在声明支持范围内可用；不支持时给可操作原因 |
| 网络 | 正常、节流、断网恢复、302、Range 不一致 | 不假完成、不错误续写，取消可清理 |
| 下载 | 短/超长分段、缺 part、并发保存、磁盘失败 | 完成文件与预期一致，索引可恢复，凭据不外泄 |
| 更新 | 正常、同大小坏包、取消立即重试、复制失败 | 错包拒绝，旧任务不覆盖新任务，旧安装/用户数据可恢复 |
| 系统入口 | 锁屏、通知、后台、音频打断、内核切换 | 控制作用于实际播放器，暂停/音量不擅自改变 |

| 隐私 | 假域名、查询/路径 token、异常值、导出/迁移 | 各出站通道一致脱敏，敏感文件权限符合平台要求 |

应使用可控的测试服务器和公开/授权样片，避免把私人服务器、账号和观看数据写入语料或报告。性能指标按固定样机和网络分别建立基线；本报告不把未测试机型的表现推广到全部设备。

## 12. 最终判断

LinPlayer 的价值和技术基础已经成立。下一阶段最能提升它作为 Emby 客户端的可信度的投入，是保证完整找片、稳定播放、可靠续播、正确下载和安全更新，再把这种保证落实到键盘、手机系统入口与电视遥控器上。

本次交付为审查报告，业务代码没有修改。两个静态门禁已运行且通过，关键问题已独立复核；报告中竞争时序、服务器兼容、实际渲染和设备表现仍需按验收矩阵验证。它们是明确的剩余风险，不是已经复现的全部用户故障。
