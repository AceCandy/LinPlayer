# 手机 Media3 连播网络恢复设计

## 目标与边界

只处理普通手机播放会话在网络异常后无法恢复连播准备的问题。当前尚无完整复现，不预设修改播放器内部参数，也不预设必须重建整个播放器。

业务命令、季内队列、播放上报和续播继续由既有 Go 核心处理；页面拥有预载许可及准备请求，`ExoPreload` 拥有 Media3 的唯一预载槽和队列源。保持单播放器，不引入流影的备用解码器。

## 当前流程与待验证位置

1. `PlayerPage` 根据实际位置、缓冲和倍速决定信息准备、视频预热与排队许可。
2. `player.prepareNext` 解析目标并返回准备请求和代理；缓冲许可单独控制 `player.warmPrepared` 与 `ExoPreload.prepare/cancel`。
3. 当前集距片尾不超过 10 秒、已缓冲到尾时，页面调用 `player.queuePrepared`，再将预载源追加到当前 Media3。
4. 实际媒体切入后，`player.advanceQueued` 接管业务身份，页面替换目标，不重复 stop/load。
5. 没有进入队列时，完播走 `switchTarget` 和正常起播；真实缓冲提示继续呈现。

优先核查“许可恢复后是否重新调度实际样本加载”“预载失败与主动中断是否区分”“下一集准备槽是否被正确回收”“异常是否污染后续多个条目”。单次排队失败不是跨集残留已经成立的证据。

## 实施策略

### 先建立故障证据

- 用现有 Robolectric、Media3 1.11.0 和受控本地媒体源注入中断、恢复；复用已有本地媒体及 HTTP 测试模式，不增加依赖。
- 保持同一播放器、预载管理器与页面，至少经过三个后续目标，不能靠重建对象让测试恢复。
- 观察真实预载读取/完成、媒体源入队、实际 transition、业务接管，以及是否发生 stop/load 降级；不能只注入 `STATE_READY` 得到假绿。
- 页面接线测试可注入状态和核心请求失败，但必须与底层预载行为测试区分，不能代替真实数据源恢复验证。

### 以复现确定最小修改

- 若故障属于页面的许可、失败请求或恢复调度，只在 `PlayerPage` 修复其拥有的状态。
- 若故障属于 Media3 预载源的失败/中断生命周期，只在 `ExoPreload` 恢复有效源和有界调度；旧回调不得写入新条目。
- 只有证据表明共享加载控制本身相关时才修改 `PlaybackBuffer/ExoEngine`；不得为推测修改默认缓存、起播阈值、解码器或每次切集重建播放器。
- 若证据要求修改 Go、公共契约、TV/流影或整体架构，先停止产品代码扩展并更新方案供用户审阅。

这不是四套待实现功能；它们是定位后的互斥修改入口。未复现时不一次性修改所有候选点。

## 兼容与安全

- 继续保留预载失败时的正常起播，不因等待预载阻塞用户手动切集。
- 不吞真实播放错误，不无限重试；取消、离页、换账号和旧请求的屏障保持有效。
- 不记录地址、凭据、条目名称、播放令牌或原始响应。确需临时诊断时仅使用枚举、计数、耗时和本地代次，结束后清理。
- 回滚以撤销本任务涉及文件为边界，不迁移配置或用户数据。

## 验证层级与未决技术项

根因、最小修复位置和真实设备复现仍待实验确认；这是技术研究项，不改变用户已确认的范围与验收要求。

自动回归证明状态恢复和生产接线；真机测试单独证明用户所见的切集体验。设备不可用时明确保留未验收项，不把测试通过写成首帧无间隙。
